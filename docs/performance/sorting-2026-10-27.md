# Sorting performance evidence — 2026-10-27

## Method

- Machine: macOS 26.6, arm64, CPython 3.15.2, local uv-managed project
  environment.
- Workload: 20,000 TXT records containing 5,000 unique addresses repeated four
  times; DNS offline; temporary local results directory; checkpoint interval
  100,000 for the cold comparison.
- Measurements: wall-clock `time.perf_counter`, sorter-reported elapsed time,
  and the existing process peak-memory metric. No network or production data.
- Baseline: commit `98ea51e`, before structured result and multi-source changes.
- Enhanced: current `feat/mailforge-local-python-sorting-003` working tree,
  including structured JSONL and quarantine support.

| Run | Wall seconds | Reported seconds | Peak memory | Unique | Duplicates |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline parity engine | 2.3429 | 2.3397 | 58 MB | 5,000 | 15,000 |
| Enhanced engine | 3.4059 | 3.4020 | 52 MB | 5,000 | 15,000 |

The enhanced run wrote 11,510,014 bytes of structured JSONL. The observed
throughput is lower because every candidate now receives an explainable,
versioned result record and the run performs a source fingerprint plus durable
output flushes. Peak memory was lower on this workload. This is a laboratory
comparison, not a production-user performance claim.

## Resume overhead

The same 20,000-record workload was interrupted at candidate 10,000 with a
checkpoint interval of 1,000, then resumed from the durable boundary:

- Interrupted prefix wall time: 2.3477 seconds.
- Resume wall time: 2.3170 seconds.
- Final reconciliation: 5,000 unique and 15,000 duplicates.

The resume measurement includes source fingerprint verification, output-boundary
restoration, SQLite index rebuild, and processing of the remaining source. It
does not claim a particular crash-recovery latency target.
