# Integration contract

The canonical future flow is:

```text
Input source
→ Validation and normalization
→ Contact, preference, evidence, and suppression policy
→ Eligible recipient selection
→ Campaign preparation
→ Authorized delivery
→ Outcome recording and reconciliation
```

For the modern outbound slice, the preparation boundary is explicit:

```text
Template + primitive contact context + local assets
→ deterministic rendered content
→ validated MIME + content hash persisted per delivery intent
→ suppression and sender-policy reservation
→ UTC/IANA schedule due check
→ explicitly authorized transport adapter
→ attempt phase, outcome, lease recovery, and reconciliation evidence
```

Prepared bytes are the reviewable handoff between composition and dispatch.
The policy database stores references and limits, never SMTP credentials.
Provider profiles are secret-free records in the current schema 8 authority; runtime SMTP/IMAP adapters
resolve credentials through an injected boundary. The SMTP adapter is now
loopback-protocol-tested and can be reached only through the canonical,
explicitly gated campaign path. Provider health, DKIM signing, unsubscribe
endpoint hosting, inbox delivery, and live external sending remain outside the
local qualification claim. See `docs/provider-interoperability-012.md`,
`docs/specs/0002-outbound-engine.md`, and
`docs/mailer-capability-inventory.md`.

The recipient policy authority is `application.eligibility.EligibilityService`
over the existing SQLite `CampaignStore`. It evaluates purpose, contact
lifecycle, optional preferences, known suppressions, available authorization
evidence, operator authorization, and current mutable state. Address-only
imports remain usable and retain `authorization_unknown`; they never create
fictional consent evidence. Suppression is authoritative over preferences and
operator declarations, and the same evaluator is used again immediately before
dispatch.

Audience preparation is owned by `application.segmentation.SegmentationService`
over the same SQLite authority. Structured imports populate typed custom
attributes and append-only membership history. Segment definitions are
versioned, registry-bound ASTs compiled to parameterized SQLite predicates;
missing values remain `UNKNOWN` and do not match ordinary predicates. Campaign
preparation records the exact source and revision, rechecks eligibility, and
freezes a durable snapshot. Each recurring `run_key` has its own snapshot and
cannot silently reuse or replace another occurrence.

Inbound evidence follows a separate durable flow:

```text
Read-only source (EML/MBOX/synthetic/loopback IMAP)
→ durable acquisition identity and cursor
→ bounded RFC 5322/MIME parse and safe preview
→ classification signals
→ exact/probable/ambiguous/unmatched correlation
→ source trust and policy proposal
→ operator review or idempotent suppression/event action
```

Acquisition is committed before processing and cursor advancement, so a
restart can resume without re-fetching consequential work. Raw bytes are
retained only according to the source retention choice. The real adapter is
TLS-protected, read-only, UID/UIDVALIDITY-aware, and size-bounded, but real
mailbox acknowledgment, cryptographic sender authentication, automatic
responses, and provider-specific trust are outside this local contract. See
`docs/provider-interoperability-012.md` and `docs/specs/0003-inbound-operations.md`.

## Boundary rules

- TXT, CSV, JSON arrays, and JSONL are supported input families during the
  migration. The new ingestion service emits normalized, syntactically valid
  addresses in deterministic first-seen order.
- Syntax validity is only a parsing result. DNS/MX evidence is a separate,
  optional enrichment result and does not establish consent or authorization.
- Contact ownership, consent, suppression/unsubscribe status, and campaign
  eligibility are policy data. They must not be inferred from an email address,
  a valid domain, or SMTP acceptance.
- The current MSORTER output files, SORTER's legacy Python-list text, and
  MAILER's preserved target/state files remain compatibility inputs until an
  operator selects an explicit snapshot. The canonical translator and state
  rehearsal are additive; no assignment in this milestone makes SQLite the
  sole live authority for unselected legacy data.
- The synthetic campaign core is exposed through `mailforge campaign`; it owns
  only the SQLite database explicitly supplied to that command. It does not
  read legacy MAILER state automatically. SMTP execution is a separate
  application API requiring both campaign authorization and the independent
  live-send gate; the CLI remains simulation-only. The exact legacy mapping and recovery rules are in
  `docs/mailer-migration-contract.md`.
- A future stable contact identifier must be generated by the authoritative
  local database and remain distinct from an address string. Legacy rows may
  be migrated only after ownership, duplicate policy, consent provenance,
  campaign status, and rollback are documented and tested.

## Delivery outcomes

The system must distinguish SMTP server acceptance, permanent rejection,
transient rejection, connection failure, and ambiguous post-DATA outcomes.
Acceptance is not inbox delivery. Ambiguous outcomes are retained for
reconciliation and are never blindly retried. Previously completed recipients
must be excluded using durable campaign state, not an in-memory set alone.

## Current compatibility obligations

The existing files and relative invocation paths are de facto compatibility
surfaces: `MSORTER` input/output files and checkpoints, `SORTER`'s staged files,
and `MAILER`'s configuration, templates, target files, and state logs. Any
replacement must be additive or provide an explicit conversion and recovery
procedure. This milestone does not perform that conversion.

## Unified sorting contract

The packaged sorting service owns the functional union of the former sorting
tools. `mailforge sort` accepts TXT, CSV, JSON arrays, and JSONL; streams source
values with a byte bound; normalizes and validates addresses; deduplicates with
temporary SQLite state; routes using configurable provider definitions; loads
disposable-domain data; optionally enriches custom domains with synchronous or
asynchronous MX lookups; writes provider files, `master.csv`, `summary.json`,
and optional `dns.json`; and persists checkpoint/resume state.

The historical `MSORTER` commands and `SORTER` scripts are retired source,
not supported entrypoints. Their staged files remain preserved data contracts:
`emails.txt` → `formatted_emails.txt` → `sorted_mails.txt`, including safe
counting of the historical Python-list representation. Use `mailforge sort`,
`mailforge transform`, and `mailforge extract-jsonl`; no live DNS lookup is
performed unless a non-offline DNS mode is explicitly selected.

The enhanced job contract accepts multiple sources in argument order and
shares one deduplication index across them. It emits versioned UTF-8 LF
`processing.jsonl` records with source provenance and deterministic reason
codes, plus an optional `quarantine.jsonl` for rejected records. A CSV master
export escapes spreadsheet formula prefixes. Resume metadata includes a source
fingerprint and output boundaries; changed inputs and unsupported legacy
checkpoints are rejected before mutation. Disposable refreshes retain the
previous dataset on failure and record source/hash/timestamp provenance in a
sidecar metadata file.

## Product capability authority

`docs/product/capability-atlas.md` is the claim ledger for the full product.
It distinguishes local implementation, synthetic simulation, partial slices,
external integration readiness, and decisions still owed. The sorting matrix
and MAILER inventory remain detailed compatibility evidence; the atlas does
not replace them.

## Local workflow automation

The visual automation path is an orchestration layer over the same authority:

```text
Trusted local event
→ idempotent enrollment pinned to a published revision
→ condition / UTC wait
→ canonical list, campaign-preparation, or operator-note action
→ durable step, run, and audit history
```

`application.automation.AutomationService` is the only workflow authority for
the web API, CLI, and bounded in-process worker. It never evaluates a private
copy of recipient policy and it never opens SMTP. Published graph revisions are
immutable; a run stores its revision id, and every side effect receives one
durable idempotency key. Source-event and once-per-contact constraints prevent
replay and self-trigger loops. See `docs/specs/0007-visual-workflow-automation.md`
and `docs/visual-workflow-automation.md`.
